Clear-cut revision plan

os-dnscrypt-routes (formerly os-dnscrypt-eu): from a gated lifecycle manager to a small, normal OPNsense plugin · draft 2026-10-12 · high-level, for discussion

In short: the plugin's real job is to write about ten lines into dnscrypt-proxy.toml: resolver names, per-resolver relay routes, lb_strategy, two booleans and an optional ECS hint. Today that job sits behind roughly 2,600 lines of lifecycle machinery (adopt, preflight, return-control, package locks, journals and hash allowlists), about 6,100 lines of tests and about 4,100 lines of review paperwork.
  • Replace that machinery with a standard OPNsense model → template → restart plugin. Save & Apply takes effect immediately.
  • Add the missing resolver/relay editor: a route matrix that blocks any relay run by the resolver's own operator.
  • Keep an optional Save & Test. It runs the candidate config in a throw-away dnscrypt-proxy on 127.0.0.1:5354, so live DNS is never touched.
  • Keep the manual two-file restore kit and the test-VM snapshot, and script the entire test-VM lifecycle.
  • Keep git history intact. All deletions are normal commits.
  • Execute as 13 work packets that agents can run in parallel, with checkbox tracking and independent review loops (§9–§11, docs/implementation/ (archived in the tag revision-process)).

3. Target architecture

How the config gets generated: wrap the stock template, don't copy it

The manual kit ships a full copy of the stock template, so it must be re-diffed after every plugin upgrade. OPNsense's template engine is plain Jinja2 with a regex_replace filter. It applies +TARGETS.D/*.TARGET in sorted order, and the last entry wins. The plugin can therefore include the stock template and patch only what it owns:

Coexistence with the manual override

The manual kit's 90-eu.TARGET and the plugin's 95-dnscrypt-routes.TARGET both map onto dnscrypt-proxy.toml, and 95 wins. So that installing the plugin never changes a working router, the disabled branch defers to the manual template while its mapping is active:

StateWhat generates dnscrypt-proxy.toml
Plugin not installedManual override if present, otherwise stock
Installed, routing disabledSame as not installed: the template includes the manual template only while its 90-eu.TARGET mapping is active, otherwise stock
Installed, routing enabledPlugin routing (wraps the stock template). The manual override is shadowed, and a notice says so.
UninstalledManual override if still present, otherwise stock

To migrate from the manual override without a gap, install the plugin, enable it and Save & Apply, then remove the manual kit files. Removing the manual kit while the plugin is disabled returns to stock.

4. Resolvers, relays and the operator rule

Each resolver and each relay carries an operator tag. When you add an entry from the catalog the tag is pre-filled from a name heuristic (strip anon-, take the first label, plus a small alias table such as cs → cryptostorm). You can always edit it. Routes are stored per resolver as references to relay rows, so renaming a relay never breaks a route.

Validation on save

The invariant (R-21): while enabled and skip_incompatible is on, every query goes through a relay or fails. dnscrypt-proxy goes direct in several cases: an empty server_names means "all servers", a DNSCrypt server without a route is used directly, and DoH servers ignore routes entirely (upstream fetchDoHServerInfo never calls route()). So only DNSCrypt resolvers with relays are accepted, every write endpoint re-checks the full rule set, and the template fails closed if a broken config gets through anyway (R-03). The template also forces doh_servers and odoh_servers off (R-02). dnscrypt-proxy applies that protocol filter even to explicitly named servers, so a resolver that later turns into DoH in the catalog is dropped rather than used directly.

5. The UI

One page, added to the existing Services → DNSCrypt-Proxy menu group. It uses standard OPNsense building blocks: a settings form, bootgrid tables with edit dialogs, the service status/restart widget and a custom route-matrix table. The top-level About and Status tabs go away. Help text lives next to each field, and a status strip replaces the evidence tables.

Interaction details

  • Save & Apply (primary) saves, validates, regenerates the config through the stock OPNsense/Dnscryptproxy template set and restarts the service once. The button shows a spinner while the restart runs (about 60 s), then refreshes the status strip.
  • Save & Test (secondary) saves without applying and starts the background test. The page polls for the result. When the test finishes, an Apply button appears in the test panel.
  • A "Saved, not applied" state is shown when the config differs from the last applied hash. This is the normal OPNsense pending-changes pattern.
  • No confirmation dialogs, except the browser's standard "unsaved changes" prompt.
  • Adding a resolver or relay opens a dialog with a searchable catalog picker that shows name, country and description. The operator tag is pre-filled and editable.

6. Apply and the optional test

Apply (default path)

  1. settings/set runs the full rule set (R-06), including the operator rule.
  2. service/reconfigure uses ApiMutableServiceControllerBase with template OPNsense/Dnscryptproxy and service dnscryptproxy, exactly like the stock plugin.
  3. Store the applied config hash and time, then re-read status.

There is no adoption, journal, lock or backup step. Rollback means editing the settings back, or unticking Enable, and applying again.

Test (optional path, testrun.py)

  1. Set one deadline for the whole run (90 s total). Every step below checks it; when it passes, the run ends as failed with timeout.
  2. Render the saved config with OPNsense's own Template(target_root_directory=/var/run/dnscrypt-routes/test), so the result is the same output Apply would produce.
  3. Patch the copy: listen on 127.0.0.1:5354, use a temp log file, turn query logs off and use local copies of the signed catalogs.
  4. Run dnscrypt-proxy -check, then start the instance. Wait for live servers until the deadline.
  5. Send 3 test queries with drill -p 5354. Parse per-resolver OK (DNSCrypt), RTT and route lines.
  6. In finally (also on timeout and crash): stop the instance, write the result JSON and delete the temp directory.

Only one test runs at a time; a second start is refused (test-start returns reason already-running, C-02) without touching the running test's result. For tests only, the binary path and the deadline can be overridden with DNSCRYPT_ROUTES_TEST_BINARY and DNSCRYPT_ROUTES_TEST_DEADLINE (C-06).

Disclosed in the UI: the test makes real outbound queries to the selected resolvers and relays.

7. Test VM: fully scripted lifecycle

This keeps the current approach: an amd64 OPNsense guest in the pinned qemux/qemu container on OrbStack, with TCG emulation, QEMU user NAT and SSH/HTTPS forwarded to 127.0.0.1 only. The manual steps recorded in the review notes become one entry point, test-vm/vm, driven by test-vm/vm.env, which holds the version, ports, subnet, ISO/image checksum and credentials for the throw-away guest.

  • Unattended install: the DVD installer is an interactive TUI. The plan is to switch to the official nano image (pre-installed, serial console) and seed config.xml before first boot. Candidate mechanisms are the boot-time importer reading from an attached MSDOS disk, or an expect script on the serial console. This is a spike; see risks.
  • Provisioning after first boot runs over SSH. It installs os-dnscrypt-proxy and applies the baseline (DNSCrypt on 127.0.0.1:5353, Unbound forwarding, optional query logging) through configctl/API, not by hand-editing.
  • Build happens inside the guest, because it is the only FreeBSD host: a pinned opnsense/plugins checkout and make package. This replaces scripts/build-local.sh.
  • Smoke tests (vm test) cover install, Save & Apply via the API, the generated TOML matching expectations, drill through Unbound, the side-instance test, disable → stock output, and uninstall → stock output.

9. Requirements

Numbered requirements are the contract between this plan and the work packets. Each packet lists the R-xx it satisfies, and reviewers check against them. Sections 1–8 explain the reasons; this table is the testable summary.

IDRequirementSource
R-01The plugin template includes the stock template. When the plugin is disabled, the output is byte-identical to what would be generated without the plugin: the manual override's template if its 90-eu.TARGET mapping is active, otherwise the stock template. The template checks the mapping itself: it includes the .TARGET file with ignore missing and tests that it maps dnscrypt-proxy-eu.toml onto dnscrypt-proxy.toml. A manual template file without its mapping is ignored. When the base service is disabled, the output is empty, as with stock.§3
R-02When enabled, the stock server_names and routes are removed, and these owned keys are injected: server_names (enabled resolvers), lb_strategy, edns_client_subnet (only when ECS is on), one route per resolver, skip_incompatible and direct_cert_fallback. The protocol filters are forced to dnscrypt_servers = true, doh_servers = false and odoh_servers = false, whatever the stock UI sets: the stock lines (always emitted) are replaced in place. If one of them is missing, the output fails closed (R-03). The result is valid TOML.§3, §4
R-03Stripping removes a stock server_names line and a stock routes block if they are present. Their absence is normal: stock emits neither while its lists are empty. The injection needs the [anonymized_dns] anchor and the three stock protocol lines (R-02). If one of them is missing (the stock template changed), the output fails closed like below, with the override-not-applied marker (C-06) instead, and the status strip reports it. Fail closed: if the model breaks the invariant at render time (no enabled resolver, an enabled resolver without relays, a dangling relay reference), the output is the stock-rendered file with server_names = ['dnscrypt-routes-invalid-config'] injected, no routes, and the invariant-violated marker (C-06). DNS stops instead of going direct. Protocol checks can't be done in the template; R-06 and the runtime check (R-10, R-13) cover them.§3, §4, §12
R-04The package ships the template and the 95-dnscrypt-routes.TARGET mapping, with no install or deinstall hooks. Uninstalling returns generation to the mappings that remain: the manual 90-eu override if present, otherwise stock.§3
R-05The model follows C-01. A fresh install seeds the vetted preset, disabled. Its canonical source is reference/effective-settings.json (C-01 Preset); the seeded model is verified against it offline (preset.json) and on the VM.§1, §4, C-01
R-06Saving is blocked when a relay has the same operator as its resolver, an enabled resolver has no relays, a relay name equals anon- + the resolver name, or an operator is empty. Enabling is refused while the catalog is unavailable, with the message "Start DNSCrypt-Proxy once so it downloads the signed resolver list." Every write endpoint (settings/set, add/set/del for relays and resolvers, reconfigure) re-checks the full rule set and refuses instead of saving partially. Deleting a relay is refused while any resolver references it. Disabling or deleting the last enabled resolver is refused while routing is enabled. Turning routing off (enabled = 0) is always allowed, so a missing catalog or a broken route can never lock the user out. While routing is enabled and the catalog is unavailable, only that change is accepted.§4
R-07Warnings, which don't block saving: a single relay, a relay name missing from the catalog, an ECS subnet other than the preset, non-empty stock lists, and skip_incompatible off. (A present 90-eu.TARGET is a status notice, R-10, not a save warning.)§4

11. Work packets and implementation process

This plan defines what to build. How it gets built is in docs/implementation/ (archived in the tag revision-process), kept as markdown so agents can tick checkboxes:

  • docs/implementation/README.md (in the tag revision-process) covers roles (coordinator, implementer, reviewer, owner), the packet workflow with git worktrees, the review loop, finding severities, the termination rule, the gates (ready for review, merge approval, milestone acceptance) and test-VM scheduling.
  • work-packets.md (in the tag revision-process) is the coordinator's status board and milestone checklist.
  • wp/WP-01.md … WP-13.md hold one packet each: owned paths, task and acceptance checkboxes, review rounds and findings. Each packet owns its own file, so parallel agents never conflict on tracking.
  • milestones.md (in the tag revision-process) holds the two-lens milestone reviews (correctness and contracts; user and operator view).

12. Risks and spikes

RiskMitigation
Strip regexes break when the stock template changes its server_names/routes formatting.Render tests pin today's stock template. The VM smoke test renders the installed stock template. If the [anonymized_dns] anchor is missing, the template fails closed (DNS stops rather than going direct) with the override-not-applied marker, and the status strip reports it, so the change can't go unnoticed.
Unattended OPNsense install and config seeding on the nano image.Time-boxed spike in WP-05. If it fails, the fallback is a one-time manual install kept as a reusable "golden" qcow2 at $VM_STATE_DIR/golden.qcow2, with everything after that scripted.
The side instance competes with the running service for CPU and catalog downloads.Copy the cached signed catalogs into the temp directory, cap the run at 90 s and always kill the instance in finally.
Installing the plugin on a router that uses the manual override.A disabled plugin defers to the manual template while its 90-eu mapping is active (an orphan template file is ignored), so nothing changes until routing is enabled. Render tests (WP-02) and the VM coexistence check (WP-11) cover it.
Operator guesses are wrong, for example for shared hosting.The tag is always editable. The UI says it is an application-level separation, not proof against collusion, which matches the README caveat.
A resolver changes protocol or loses its route after saving (catalog update).Prevented: the forced protocol filters (R-02) drop a resolver that turns into DoH or ODoH, and a resolver without a valid route can't be used. As a backstop, the runtime log check raises a "direct connection detected" alert, and Save & Test fails such resolvers.
The old v0.1 plugin on the VM left a pkg lock and managed files behind.No migration code: the VM is rebuilt by the scripts.
